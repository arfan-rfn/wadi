This document sits on top of `docs/entity-access-plan.md`, which records the 27 decisions (Q1 to

Amendments tagged `R1-n` came from the independent spec review. Its code citations for R1-1,

## Problem statement

Wadi marks database calls in each endpoint's flow (`sink: db`) and lists entities per service
(`data_models`). Nothing joins the two, and no call carries a verb. A reader of the map, human or
agent, cannot answer "which entities does this endpoint touch, and does it create, read, update or
delete them?" Architecture goal 5 names this and no phase plans it.

## What makes this cool

- An agent that knows `POST /orders` creates `Order` and `GET /orders/{id}` reads it can order a
  stateful test (create, read, update, delete) without guessing. That serves the test-generation
  case in product goal 10 through the new `entity_usage` MCP tool.
- Each verb comes with its basis. The reader sees "update, because the saved object was read
  here" and can check it against the source in the next pane.
- The published attempt at this on TrainTicket merged create and update after its split rule
  scored 74%. Wadi claims a single verb only where a basis has passed a measured bar, and says
  "create or update" everywhere else.

Follow-ups this makes cheap, none of them in this phase:

- Shared-table detection. Two services whose entities map to the same storage name break
  database-per-service.
- Lifecycle gaps. Entities that an endpoint creates and none deletes, or that are read and never
  written.

## Constraints

- P5 and P6: Joern stays stock. The Scala pass emits raw facts and stays declarative. The Python
  worker classifies.
- P4: the extraction worker is the only writer of endpoint and ICFG documents. The reverse and
  cross-service views are composed at read time and nothing is stored for them.
- P10: an unreadable verb is `unknown` and an unsplittable save is "create or update". Neither is
  dropped or guessed.
- Phase 2.9.5 measured what reading full endpoint documents costs (114 MB, 11 s for one ICPC
  service). Every new read path in this phase reads a projection and is measured.
- Spring Data repositories only in v1 (Q4).

## Premises

All four were agreed in the session. Premise 4 is narrowed below by R1-4.

1. This is the right problem. Goal 5 names it, and a database call in the map has no entity and
   no verb today.
2. A plain `create` or `update` claim ships only if its basis passes a precision bar on
   hand-labeled saves. The bar is set before measuring. A basis that misses it is demoted to
   "create or update". The existence-guard basis (Q23) is the one most likely to miss.
3. Q12 changes. In JPQL a join target is an association path, so the reader resolves it through
   the entity's field type. Entity names are matched case-sensitively against the service's own
   entities. Only native SQL reads table names.
4. The phase stores no new collection. It reuses `sink=db`, `data_models` and read-time
   composition. Reading the repository's type argument is new code until the probe in next step 2
   says otherwise.

### Prior work behind premises 2 and 3

- Abdelfattah, Schiewe, Curtis, Cerny and Song, "Towards Security-Aware Microservices: On
  Extracting Endpoint Data Access Operations to Determine Access Rights", CLOSER 2023. The paper
  extracts per-endpoint CRUD on TrainTicket (41 services, a different revision from
  `train-ticket-aitest`). It reports 1,322 of 1,364 ground-truth operations identified. Of the 42
  misses, 38 came from classifying create against update, and the paper says its save rule
  "yields 74% accuracy against the ground truth" without giving the denominator. Its Listing 5 is
  a save that is a create or an update depending on whether `findByIndex(0)` returned null. Its
  Listing 6 is an update done by saving a newly created object after an existence check. Both
  shapes appear in the plan's train-ticket sample. Figures are as reported by a summarizing
  fetch of the paper, read twice, and are not checked against the PDF.
  https://scitepress.org/publishedPapers/2023/117075/pdf/index.html
- A practitioner write-up on a Spring Boot analyzer reports that reading
  `LEFT JOIN FETCH p.releases r` as SQL produced a table called `fetch`, and that
  `select o from Order o` was read as the keyword `order`. https://nljug.org/?p=11528
- The other tools found (the Microservice Dependency Matrix, DENIM) link endpoints to entities
  and do not classify create against update.

## Approaches considered

### Approach A: name-level facts only

Rejected. Every save would read "create or update" and ICPC's 688 `@Query` methods, at least 617
of them named queries, would stay `unknown`. It stops where the 2023 paper stopped and works
against the Q3 instruction.

### Approach B: the plan as decided, with the split behind the precision gate

Chosen. See below.

### Approach C: B scored against runtime SQL

Rejected for this phase. The statement log gives an exact INSERT or UPDATE, but it needs every
corpus running with a database and valid requests, and nobody knows whether ICPC can run. It
stays a candidate for settling the dirty-checking question on ICPC (Q25).

## Recommended approach

Approach B. The 27 decisions hold except where this section amends them.

### Order of work

Name-level facts land first: entity from the repository's type argument, verb from the method
name, every save "create or update". The train-ticket slice reaches REST, MCP and the UI in that
state. The create and update split follows as its own milestone.

In the name-level slice a repository method that carries `@Query` or `@Modifying` publishes
`unknown`. The method name never decides the verb for an annotated method (R1-12).

### The gate (premise 2)

- **What is scored.** Each basis that can produce a single verb (`argument-origin`,
  `existence-guard`) is scored on its own, and each verb it can emit is scored on its own.
- **Outcomes.** A basis with fewer labeled members than the minimum gets no verdict, and no
  verdict means demoted. A single verb on a site labeled "either" counts as a miss (R1-9).
- **The bar.** The user writes the number, and whether it is a point estimate or a lower
  confidence bound. The two differ: 19 of 20 correct is a 95% point estimate, and its one-sided
  95% lower bound is about 0.78. A lower bound of 0.95 with no misses needs 59 members (R1-9).
- **Scope of a verdict.** The gate is a release gate on the rule. A basis must pass on every
  corpus that has a labeled sample, and a failure on any one demotes it everywhere. Train-ticket
  is the first sample. The twenty-endpoint checks on yas and ICPC supply the others (R1-10).
- **Where it lives.** The labels are a file in the repository, keyed by service, file and line
  at a pinned corpus commit. The per-basis verdict is a flag in the verb table the classifier
  reads. A change to a basis's raw facts or classification resets its flag until a re-score. The
  scorer reads a stored export, not the live stack (R1-13).
- **What a demoted fact looks like.** It publishes "create or update" and keeps its basis and
  its candidate verb as evidence that is not a claim (R1-11).
- **What the goldens pin.** The fixture fixes the raw facts and the candidate verb per basis.
  The published verb is a function of the flag, and both flag states are tested (R1-11).
- **The labeled set.** Distinct save call sites in train-ticket, after removing copies vendored
  across services, each labeled create, update or either from the source before any rule output
  is looked at. The "constructed after a lookup" bucket is about 71 before removing copies. The
  deduplicated count per basis is reported before the minimum is set, and the members opened
  for the plan are flagged as not blind.

### Amendments to the plan's decisions

- **Q9, lambda-hosted database calls (R1-1).** `unreachable_sinks` cannot report them. It keeps
  only `http-client` sinks whose method is outside the export closure, and lambda bodies are
  inside it. The worker counts `sink=db` calls that are in the export but in no endpoint flow,
  as their own accounting bucket. Database calls in dead code outside the closure are not
  inventoried in v1.
- **Q11, the unsplittable save (R1-5).** It gets its own operation value in the contract, shown
  as "create or update", and not a fact that carries both verbs. Q16 reads a verb as "some path
  performs this", so two verbs on one fact would claim both happen. The value is carried
  unchanged through the endpoint summary, both REST routes and all three MCP tools, and is
  counted apart from the create and update columns on every one of them.
- **Q14, the unit of accounting (R1-2).** The unit is the repository call site. The export picks
  one call per statement today, so `repo.save(repo.findById(id).get())` would yield one fact. A
  flow node carries a list of entity facts and the Scala pass emits one raw fact per
  sink-tagged call in the statement. The fixture gains that case.
- **Q1 and Q10, where the entity comes from (R1-4).** The entity is resolved from the
  receiver's declared repository type, because a method declared on a base interface names a
  type whose parameter is unbound. Nobody has checked which CPG node holds the text of an
  `extends JpaRepository<Order, String>` clause. A probe on a fixture CPG settles that first.
  If no node holds it, the pass reads the declaration lines from the file. A chain the reader
  cannot bind yields "entity undetermined".
- **Q12 and Q15, what the entity record needs (R1-3).** The export writes each field's erased
  type and a null storage name today. The Scala step emits each entity field's declared type
  text and the `@Table` or `@Document` storage name. A JPQL join target resolves through the
  field's declared type text. `DataModel.relations` stays unpopulated (Q17). Until this lands a
  join target reads "entity undetermined".
- **Q18, the reverse view's read shape (R1-8).** `/auth` reads every full endpoint document in
  the snapshot. `GET /snapshots/{id}/entities` and `entity_usage` read a projection (endpoint
  identity plus the entity summary) and the snapshot's data models in one query.
- **A snapshot analyzed before this phase (R1-6).** The stored summary distinguishes "not
  analyzed" (absent) from "analyzed, none found" (empty). The Data list gains a sixth state for
  it, and `/entities` and `entity_usage` say the snapshot predates entity facts.
- **The "no database call" state (R1-7).** It reads "no repository call found" and shows the v1
  limits beside it: other persistence mechanisms, setter updates, lambdas and cascades are not
  read. Withholding the negative when the endpoint reaches an unmodelled persistence type is a
  TODO for the ICPC milestone.
- **Counting.** A save classified "create or update" has its own count in the system matrix.

## Open questions

1. The precision bar: the number, point estimate or lower bound, and the minimum labeled members
   per basis. The user sets it before labeling starts.
2. The scope of a verdict. This document proposes a release gate across all labeled corpora. The
   reviewer's alternative is that a basis publishes single verbs only on a corpus where it was
   scored, which would leave every user system without labels at "create or update".
3. Who labels. If Claude drafts the labels, the user reviews them before any rule output is
   shown.
4. Whether the CLOSER 2023 ground truth is obtainable and how much of it maps onto
   `train-ticket-aitest`.
5. Which CPG node, if any, holds a repository's `extends` clause text (R1-4). The probe answers
   it.
6. How ICPC performs updates. Q25 measures it when the ICPC milestone starts.
7. Whether the wadi ICFG includes `@ModelAttribute` methods. Train-ticket has none.
8. Whether ICPC's database calls are unmarked today (`SpringPacks.scala:686`). Read from code,
   not confirmed on a snapshot.

## Success criteria

- The `spring-data-crud-matrix` fixture has a named golden for each shape in the plan's section
  4, plus: a JPQL join over an association path, an entity named like a SQL keyword, two
  repository calls in one statement, and an annotated query method in the name-level slice.
- On a train-ticket snapshot, every repository call site in the export is accounted for: bound
  to an entity and a verb, `unknown` verb, undetermined entity, or in no endpoint flow. The
  buckets add up to the total.
- No basis publishes a single verb without a passing verdict, and both flag states are tested.
- An independent oracle counts repository call sites from comment-stripped source. Every
  disagreement with wadi is opened and explained.
- Twenty endpoints per corpus are opened by hand, including ones where the oracle and wadi agree.
- `endpoint_detail`, `endpoint_icfg` and `entity_usage` are each checked through the MCP server,
  including that a reader can tell one "create or update" save from one create plus one update.
- Payload and latency are measured before and after on the endpoint list route, and measured on
  ICPC for `/entities` and `entity_usage`.
- The UI renders the six Data list states, and a failed fetch shows no claim.

## Distribution plan

The existing pipeline covers this. The feature ships in the wadi stack with a contracts bump and
an export bump. `make schema` regenerates the frontend types. A snapshot analyzed before the
phase reports that it predates entity facts until it is analyzed again.

### R1-1 — feasibility (blocking)

**Problem**

> The design keeps Q9 ('All 27 decisions hold'), and its first success criterion requires a golden for the plan's shape 'A save inside a lambda (reported in unreachable_sinks)'. The existing section cannot report it. unreachableSinkObjs (joern-platform/src/main/scala/wadi/export/WadiExport.scala:1749-1770) keeps only sinks whose enclosing method is outside the export closure (line 1753) and whose kind starts with 'http-client' (line 1761). Lambda bodies are inside the closure: reachableClosure follows METHOD_REF targets (lines 311-314), and docs/foundation-hardening-plan.md A1 records that they enter the export and reach no endpoint ICFG. So a sink=db call in a lambda is in neither unreachable_sinks nor any endpoint graph today, and the criterion 'the accounting adds up to the total number of database calls' has no bucket for it.

**Remedy**

> Correct Q9 before planning. Lightest option: have the worker, which knows both sets, inventory sink=db calls that are in the export closure but in no endpoint ICFG, and count them in the entity accounting. Decide separately whether db sinks outside the closure (dead code, which train-ticket has a lot of) are inventoried too, because widening unreachable_sinks to kind 'db' pulls those in. Update the fixture shape's expected output to match.

### R1-5 — consistency (blocking)

**Problem**

> Q11 stores an unsplittable save as a fact carrying both create and update, and Q16 defines a fact as 'at least one path through this endpoint performs this operation'. Read together, a both-verbs fact claims the endpoint creates and also updates, when the analysis knows only that it does one of the two. The Counting amendment fixes this for the system matrix alone. The endpoint summary, the list row, GET /snapshots/{id}/entities, endpoint_detail, endpoint_icfg rows and entity_usage are not covered, and once verbs are merged per entity in a summary, 'one save that is create or update' and 'one create plus one update' look identical. ### R1-9 — clarity (blocking)

**Problem**

> Open question 1 proposes a 95% bar with a minimum of 20 labeled members, and premise 2 demotes a basis that 'misses' it. As a point estimate this does not show 95% precision. At 20 members the bar allows one miss (19 / 20 = 0.95). The exact one-sided 95% lower bound on true precision is 0.05^(1/20) = 0.861 for 20 of 20 correct and about 0.784 for 19 of 20. Showing a lower bound of 0.95 with zero misses needs ln(0.05) / ln(0.95) = 58.4, so 59 members. Three outcomes are also undefined: what a basis publishes when it has fewer than the minimum ('no verdict' is not 'misses'), how a site labeled 'either' scores when the basis emits a single verb, and whether a basis is scored as a whole or per verb.

**Remedy**

> When the user writes the number, also write whether the bar is a point estimate or a lower confidence bound, and state the three outcomes. Safe defaults: no verdict means demoted, a single verb on an 'either' label counts as a miss, and each verb a basis can emit is scored on its own.
