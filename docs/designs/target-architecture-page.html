Wadi target architecture

Wadi reads several kinds of evidence about a microservice system and joins them into one map. This page shows every part, what it connects to and which parts exist today.

Four rules the design follows

One reader per kind of evidence

Source code, deployment config, contracts and runtime data each get their own reader.

Each reader keeps its own records

A reader writes only to its own collection. Each run writes a new set, and a snapshot lists the sets it uses, so older snapshots never change. No reader edits what another one wrote.

Records are joined when the map is read

The join keeps every source's value and says how many sources agree. Wadi discards nothing at write time. Call edges join when the stitcher writes them, because the graph database is built from them.

A model writes rules, never facts

Analysis runs with no model and no API key. A model only drafts rules, and wadi tests them. A model's disagreement never changes a fact's status.

What has to be built

  • Export per service. A service bundle leaves out stitched edges and the coverage report, because the receiver computes those for its own set of services.
  • A bundle as a kind of source in a system, next to a git URL and a local path. The decision record already reserves this.
  • An import job in the extraction worker. The orchestrator accepts the bundle and the worker writes it, so each collection keeps one writer.
  • An origin on every record: analyzed here, or imported from a named bundle.
  • A service id that does not depend on a folder path on one machine.
  • A snapshot that can be made of bundles as well as commits.
  • A round-trip test: export a service, import it into an empty install, export it again and compare its records without the envelope fields.

Which process talks to which

The services that build the map never call each other. Each one reads and writes MongoDB, and the orchestrator hands out work as jobs in that database. Only the extraction worker talks to Joern. The planned auth module adds one more direct connection. The access prober sends every test request through the credential broker.

  • Any service can be restarted or replaced without the others noticing, because they share only the database.
  • Only the credential broker reads secrets. It reads the identity profile from MongoDB and writes only its request log, which never holds a credential.
  • Joern holds no data that matters. It receives source files and returns one export file per service.
  • Reading the map never starts an analysis. The REST API and the MCP server read stored records.

Inside one analysis of one service

The static analyzer is the extraction worker and the Joern container working together. Inside Joern, wadi's code runs in a fixed order. What wadi knows about each framework arrives as data.

  1. The orchestrator creates an extract job for a snapshot.
  2. The extraction worker claims the job and checks out the repository at the pinned commit.
  3. The worker finds each service, its language and its libraries, and picks the packs that match.Planned
  4. The worker copies those packs and the system's learned rules into the shared volume and records their hash.Planned
  5. Joern parses the service, runs the language profile, the rule engine and the plugins, and writes one export file.
  6. The worker checks the file against the contracts and stores it as code facts.
  7. Joern drops the code graph. The cached copy can be deleted at any time.

What the fold tells a reader

Every fact in the map carries a status that says which sources back it.

StatusMeansExample
confirmedTwo or more sources agree.The code declares GET /orders/{id} and a trace shows it being called.
static onlyOnly the code shows it. This is not an error.An endpoint that no test or trace has exercised.
observed onlyRuntime data shows it and the code analysis does not.A call made through a client wrapper the rules do not cover yet.
declared onlyA spec or a deployment file states it and no code was found.An OpenAPI path whose handler was removed, or an ingress route to no endpoint.
contestedTwo sources give different values.The spec marks a field as required and the code treats it as optional.
  • Only a source that is independent of the code can confirm a fact. A spec generated from the same annotations is a check, not a confirmation, and a file two readers both read counts as one source.
  • Each fact lists the readers that covered it, so "static only" says whether anything else looked.
  • Two sources from different builds, or a name that matched two services, are not comparable. That result never counts as agreement or conflict.
  • Only readers that run with no model can make a fact contested.

The three amber statuses are the gaps that learn mode works on.

Records from different readers join because each one carries keys that any source can compute.

Every record also carries a scope: the commit, the environment and, for runtime data, the time window. A name that matches two services stays ambiguous and one that matches none stays unmatched. The join never picks one.

The learn loop

Learn mode runs only when someone starts it. The only thing it adds to analysis is a rule. The auditor's disagreements and counts are reports, never facts.

  1. Find. Wadi lists the gaps: unknowns the map reports, facts that are observed only, declared only or contested, and disagreements from an auditor that re-reads sampled endpoints without seeing the map.
  2. Draft. A model reads the source around one gap and drafts a rule.
  3. Check. Wadi runs the draft inside a real extraction and compares the result with and without it. A draft may only add facts.
  4. Approve. A person accepts or rejects the rule. Wadi remembers rejections. Whether a rule that is not about authorization applies before this step is still open.
  5. Replay. The approved rule is stored with the system and runs on every later analysis, with no model.

Identity and access

Every service decides who may call it in its own way. Spring Security alone can allow, deny or skip a request in a dozen places, and a gateway in front of the service can change the answer again. Wadi therefore keeps two answers for every endpoint. One is the rule it read. The other is the result it measured on a running test environment.

The goal is that an agent or a test generator can call any endpoint as any kind of user and know what should happen. Nothing in this section is built. Wadi 0.9.0 reads access rules from Spring code and stops there.

A test names an identity, never a token

A test says admin or customer B. A recipe for that identity produces the credential when the test runs, so the same test works on a laptop and in staging.

The running system gives the verdict

What wadi reads from code, config and specs is a prediction with its reason. What a test environment answers is the measurement. The map shows both.

Only the broker reads secrets

Analysis still runs with no secret and no API key. An agent asks the broker to send a request as an identity and never sees a password.

How a test gets its credential

A recipe can run once before a test run, or at the moment of a request. The broker keeps the credential until it expires. How the recipe makes the credential depends on what the test runs against.

  • Recipes use the Web Fuzzing Commons authentication format, which EvoMaster, Schemathesis and other API test tools already read.
  • For single sign-on with a second factor, a person logs in once and the broker reuses that session.

What a person supplies once per system

  • The names of the test identities and the roles and authorities each one has.
  • For one service running alone, a test configuration that trusts the mock issuer.
  • For a whole system, one test user per identity at the identity provider, with its secret in the secret store.
  • Where a second factor is required, an exclusion for the test users or one login whose session the broker reuses.

Limits

  • A measurement holds for the identities tried, in one environment, at one time.
  • Checking that a user sees only their own records needs two identities with the same role and data that each one owns. This comes after role checks.
  • A role kept in a service's own database needs a setup step that creates the user.
  • A mock token can carry roles the real identity provider would never issue together. Mock tokens should copy the claim layout of one real token per identity.
  • The measured result is what the system does. What it should do still comes from a person or a spec. A request that fails validation, a failed login or an answer from the wrong route reads as inconclusive.

How the broker enforces the safety rules

  • The identity profile lists, for each test environment, the exact destinations a credential may go to: scheme, host, port and path prefix. The broker checks every hop, refuses everything else and follows no redirect off the list. No production destination is on any list, and a missing list means no request.
  • Every request through the broker is read-only, an agent's included. The first version sends only the operations a fixture lists, and a person can allow more per environment.
  • Each caller has its own token and may use only the identities and environments it is bound to.
  • The broker logs every request without the credential. The first version returns only the status and whether each fixture check held, because a credential can sit anywhere in a body.
  • The mock issuer has its own key for each test environment and its own issuer name, with short expiry. Only the test deployment trusts it. A service that checks tokens with a key written into its own code needs that key from the owner instead, and that recipe stays off until the owner records that production rejects the key.

The hub

The hub is not a new service. It is the same stack deployed once for an organization. Each team runs wadi on the services it owns and sends one bundle per service to the hub.

How a team sends a service

  1. The team's CI runs wadi on the services it owns, at one commit.
  2. A publish command exports one bundle per service and sends each one to the hub's REST API with the team's token.
  3. The hub's orchestrator checks the manifest: the schema version, the record counts, the branch and whether this team owns the service. A bundle from a branch the map does not follow is stored and starts no snapshot. When the map follows one branch, so is a bundle whose commit does not descend from the one the current map holds: the publish command checks descent in the team's own repository, and the hub admits the bundle only if the commit it checked against is still current. A service's first bundle, a map that takes the newest bundle from any branch, and a local or folder import skip that check. Otherwise the orchestrator creates a pending snapshot and its import job, and a sweep fails a pending snapshot left without a job.
  4. The pending snapshot lists the new bundle and every other member of the current map. The hub's worker checks the new bundle as a whole and stores its records as a member of that snapshot. The unchanged services come from the current map, copied or listed as decision D5 settles. Each imported fact keeps the team, commit, wadi version and rule hash it came from.
  5. The stitcher runs across all of them. The snapshot becomes the current map only when it succeeds. Until then the previous snapshot stays current, and a read of a pending or running snapshot returns only its status.
  6. The coverage report lists the age of every bundle and of every carried member, so a stale service is visible before anyone trusts an answer.
  • Sending again a bundle that is already the service's current member changes nothing, because its identity comes from the service, the commit, the wadi version and image digest, the rule hash once it exists, the role mappings it carries, the branch, the bundle kind, the library sources staged into the analysis, a digest of its records after the projection and, once deployment files are read, the commit of each other repository they came from and the environments they cover.
  • A rejected or interrupted import leaves the previous snapshot readable and unchanged.
  • The same bundle can be written to a folder and imported from that folder, for networks the hub cannot be reached from.
  • A team's own wadi can import a neighbour's bundle from the hub. A placeholder for that service then becomes a real service with real endpoints.

What a service bundle carries

PartContent
ManifestThe service id, the repository, commit and branch, the base commit it was checked against and whether it descends from it, a digest of the role mappings it carries, the library sources staged into it, a digest of its records after the projection, the wadi version and image digest, the config keys it carries, the schema version, the rule hash once it exists, the time it was produced, a count per kind of record, and whether the bundle is full or boundary-only
RecordsThe service boundary, endpoints, outbound calls, queue interactions and data models. A full bundle adds the flow graph of every endpoint. Config records and declared contracts join once those readers exist.
AccessThe access rules read for each endpoint, without raw config values, and the roles and authorities each test identity has in this service. Measured access stays on the install that measured it.
Left outStitched edges and the coverage report. The receiver computes them for its own set of services. A bundle never carries a recipe. From config it keeps only the values the receiving stitcher routes by, and strips user names, passwords and query strings from URLs. A value under such a key travels as it is, unless removing the rest would change where a call goes; then it is withheld and the call stays unresolved. A boundary-only bundle also drops text copied from the code. A full bundle carries a line of source per flow-graph node, so it goes only where the code may be read.

The decision record fixes the shape: bundles, an ingestion API on the hub, snapshots made of bundles and ownership by team. The six steps and the access row are proposals for the mechanics. docs/bundle-import-and-hub-plan.md describes them.

Suggested build order

  1. A scorer and ground truth, a service id that does not depend on a folder, and fixes for the facts known to be wrong.
  2. An origin on every record, and a snapshot that can list imported bundles and counts as current only after it succeeds. A restitch of the newest snapshot whose filling jobs all succeeded, the current map or a newer one whose stitch failed, makes a new snapshot with that snapshot's members. An import or an analysis keeps the members of the current map it does not replace.
  3. Export per service and bundle import, proven by two services analyzed apart and imported together.
  4. The identity profile and the credential broker with its mock issuer and its safety checks, proven on one service running alone.
  5. The access prober and the access table, first with one fixture's requests and expected answers.
  6. The config reader for Kubernetes and Helm, with the access rules of gateways and meshes, built against a fixture first.
  7. The rule engine and the base packs.
  8. The declared reader, then the auditor.
  9. Real login recipes, for tests against a whole system.
  10. The trace importer.
  11. The hub: the publish command, ownership by team and authentication for a shared install.

Import comes before identity because it proves the hub with the smallest change to records. Identity stays fourth and fifth because test generation depends on it. A review by three models on 2026-11-17 led to this order.
